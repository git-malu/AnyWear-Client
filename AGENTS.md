# AnyWear Client - Agent Instructions

Welcome to the **AnyWear Client** repository. This document provides critical context, structure, and strict guidelines for AI agents working on this frontend application.

## 📌 Project Overview

- **Purpose**: This repository focuses on building the frontend components for the AnyWear Application, targeting both Desktop and Mobile platforms using a single codebase.
- **Core Stack**: Tauri (v2), React 19, TypeScript 5, Vite, Tailwind CSS v4, Zustand, TanStack Query (React Query v5), and Axios.
- **Related Repositories**:
    - `AnyWear-Service`: The backend service (Node.js/Hono/Drizzle).
    - `AnyWear-Meta`: A Git submodule utilized by this application for metadata management (OpenAPI definitions).

## 🛠️ Build, Lint, and Test Commands

Agents must strictly use `pnpm` for all dependency management and script execution. Avoid `npm` or `yarn`.

### General Commands
- **Install Dependencies**: `pnpm install`
- **Run Development Server (Web)**: `pnpm dev`
- **Run Tauri Desktop App**: `pnpm tauri dev`
- **Build for Production**: `pnpm build` (compiles TS and builds Vite)
- **Regenerate API Client**: `pnpm orval` (Must be run after any changes to `AnyWear-Meta/api/anywear_openapi.yaml`)

### Type Checking & Linting
- **Type Check**: `pnpm tsc --noEmit`
  *CRITICAL: Agents must run this command after making modifications to TypeScript files to ensure no type regressions or interface mismatches occur.*
- **Linting**: Run ESLint via `pnpm lint` (when configured).

### Testing (Vitest & React Testing Library)
Vitest is the standard test runner for this repository. It is API-compatible with Jest but optimized for Vite.
- **Run All Tests**: `pnpm test` (or `pnpm vitest`)
- **Run a Single Test**: `pnpm vitest run path/to/file.test.ts`
- **Run Tests in Watch Mode**: `pnpm vitest path/to/file.test.ts`
- **Run Coverage**: `pnpm vitest run --coverage`
*Note: When generating or fixing tests, ensure you are mocking Axios/Orval hooks correctly using tools like MSW (Mock Service Worker) or `vi.mock()`.*

## 🏗️ Architecture & Directory Structure

- `src/api/`: API integration layer.
  - `endpoints/` and `model/`: **DO NOT EDIT MANUALLY**. These are auto-generated by Orval.
  - `custom-instance.ts`: The Axios custom instance with auth interceptors. (Safe to edit).
- `src/layouts/`: Global wrapper components (e.g., `AuthLayout`, `MainLayout`).
- `src/pages/`: Route-specific page components (grouped by feature, e.g., `auth/`, `wardrobe/`).
- `src/components/`: Reusable, generic UI components (buttons, modals, inputs).
- `src/store/`: Zustand state management stores (e.g., `authStore.ts`).
- `src-tauri/`: Rust backend specifically for Tauri desktop/mobile system bindings.
- `AnyWear-Meta/`: Git submodule containing the single-source-of-truth OpenAPI spec.

## 📝 Code Style & Guidelines

### 1. React & TypeScript Standards
- **Functional Components**: Use functional components with standard `export default function ComponentName() {}` syntax instead of arrow functions for top-level exports.
- **Strict Typing**: Avoid using `any` or `ts-ignore`. Utilize the auto-generated types from `src/api/model/` whenever interacting with API data. If a generated type lacks a field, investigate the OpenAPI spec in the `AnyWear-Meta` submodule first.
- **Hooks**: Use generated TanStack Query hooks (e.g., `useGetWardrobe()`) from `src/api/endpoints/` for all network requests. Do not use raw `fetch` or `axios` directly in components unless for specialized tasks like binary S3 uploads.

### 2. State Management
- **Server State**: Always rely on TanStack Query (`useQuery`, `useMutation`) for remote data fetching, caching, loading states, and synchronization. Do not duplicate server state in Zustand.
- **Client/Global State**: Use Zustand (`src/store/`) for cross-component global state (like user authentication status or UI theme).
- **Authentication State (Event-Driven)**: AWS Amplify is the single source of truth for authentication. Zustand acts as a synchronous UI mirror. The `AuthListener` in `App.tsx` listens to Amplify Hub events (`signedOut`, `tokenRefresh_failure`) and automatically clears Zustand's memory. Always use `logout()` in `useAuthStore` to explicitly trigger `signOut()` from Amplify.
- **Local State**: Use `useState` or `useReducer` for simple, isolated UI state (e.g., modal visibility, form inputs).

### 3. Styling (Tailwind CSS v4)
- **Utility-First**: Strictly adhere to Tailwind utility classes.
- **Tailwind v4 Setup**: Note that v4 uses `@import "tailwindcss";` in the CSS file rather than the older `@tailwind` directives.
- **No Custom CSS**: Avoid adding styles to `index.css` or creating `.css` modules unless absolutely necessary. Rely entirely on Tailwind v4's arbitrary values (e.g., `w-[150px]`) if standard utilities fall short.
- **Class Merging**: When passing `className` props conditionally, prioritize clean template literals or utility libraries like `clsx` and `tailwind-merge`.

### 4. Naming Conventions
- **Components/Pages**: PascalCase (e.g., `WardrobePage.tsx`, `AddItemModal.tsx`). Keep names descriptive.
- **Files/Utilities**: camelCase (e.g., `authStore.ts`, `custom-instance.ts`).
- **Types/Interfaces**: PascalCase, typically matching the domain entity (e.g., `ClothingItem`).
- **Constants**: UPPER_SNAKE_CASE (e.g., `AXIOS_INSTANCE`, `MAX_FILE_SIZE`).
- **Hooks**: Prefix with `use` (e.g., `useAuthStore`, `usePostAuthLogin`).

### 5. Error Handling
- **API Errors**: Utilize the `error` object and `isError` boolean returned by TanStack Query's `useMutation` and `useQuery`. Do not rely solely on `try/catch` around the mutate functions unless using `mutateAsync`.
- **User Feedback**: Always provide visual feedback for errors (e.g., inline red text for form validation, toast notifications for global errors) rather than silent failures or raw `console.log`.
- **Global Interception**: Handle generic network errors (like 401 Unauthorized) within `src/api/custom-instance.ts` by intercepting the Axios response, clearing the Zustand auth store, and forcing a redirect to `/login`.

### 6. Imports
- Use a logical ordering to keep files clean and readable:
  1. Built-in React/Hooks (`import { useState } from 'react';`)
  2. Third-party libraries (`import { useNavigate } from 'react-router-dom';`)
  3. API Hooks and Models (`import { useGetWardrobe } from '../../api/endpoints/...';`)
  4. Local Components, Stores, and utilities (`import { useAuthStore } from '../../store/authStore';`)

## 🤖 Agent Operating Rules & Workflows

1. **API Synchronization Workflow**:
   If a frontend feature requires a backend change:
   - First, navigate to the `AnyWear-Meta` submodule.
   - Edit the relevant OpenAPI specification (e.g., `AnyWear-Meta/api/anywear_openapi.yaml`).
   - Run `pnpm orval` in the `AnyWear-Client` root.
   - Inspect the newly generated interfaces in `src/api/model/` before utilizing the newly generated hook in your components.

2. **Never Assume Type Structures**:
   When fixing TypeScript errors involving API data (e.g., `Property 'imageUrl' does not exist on type 'GetWardrobe200Item'`), always use the `cat` or `read` tools to inspect the generated models in `src/api/model/` to understand the exact shape of the payload before guessing.

3. **Verify Everything**:
   After writing or refactoring code, run `pnpm tsc --noEmit` to ensure you haven't introduced type errors. Do not declare a task "complete" without verifying the types align.

4. **Preserve Submodule Integrity**:
   Treat the `AnyWear-Meta` submodule as a critical architectural boundary. Follow the documentation and guidelines inside `AnyWear-Meta/AGENTS.md` when making cross-repository changes.
