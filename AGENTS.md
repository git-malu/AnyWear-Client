# AnyWear Client - Agent Instructions

Welcome to the **AnyWear Client** repository. This document provides critical context, structure, and strict guidelines for AI agents working on this frontend application.

## 📌 Project Overview

- **Purpose**: This repository focuses on building the frontend components for the AnyWear Application, targeting both Desktop and Mobile platforms using a single codebase.
- **Core Stack**: Tauri (v2), React 19, TypeScript 6, Vite, Tailwind CSS v4, Zustand, TanStack Query (React Query v5), and Axios.
- **Related Repositories**:
    - `AnyWear-Service`: The backend service (Node.js/Hono/Drizzle).
    - `api`: A Git submodule utilized by this application for metadata management (OpenAPI definitions).

## 🛠️ Build, Lint, and Test Commands

Agents must strictly use `pnpm` for all dependency management and script execution. Avoid `npm` or `yarn`.

### General Commands
- **Install Dependencies**: `pnpm install`
- **Run Development Server (Web)**: `pnpm run dev`
- **Run Tauri Desktop App**: `pnpm run tauri dev`
- **Build for Production**: `pnpm run build` (compiles TS and builds Vite)
- **Preview Production Build**: `pnpm run preview`
- **Regenerate API Client**: `pnpm run orval` (Must be run after any changes to `api/anywear_openapi.yaml`)

### Type Checking & Linting
- **Type Check**: `pnpm tsc --noEmit`
  *CRITICAL: Agents must run this command after making modifications to TypeScript files to ensure no type regressions or interface mismatches occur.*
- **Linting**: Run ESLint via `pnpm lint` (when configured).

### Testing (Vitest, React Testing Library, and Playwright)
Vitest is the standard unit/component test runner. Client-owned Playwright browser integration tests mock Service and cloud boundaries; they do not require a running Service or database. Optional local browser exploration is supplementary UI feedback. Real cross-repository system tests and release evidence belong in `AnyWear-E2E` and run only in Beta and later stages; do not run or gate that suite in dev.
- **Run Tests in Watch Mode**: `pnpm run test`
- **Run All Tests Once**: `pnpm run test:run`
- **Run a Single Test**: `pnpm exec vitest run path/to/file.test.ts`
- **Run Coverage**: `pnpm run test:coverage`
- **Run Browser Integration Tests**: `pnpm run test:browser` (If Chromium is missing, run `pnpm exec playwright install chromium`).
*Note: When generating or fixing tests, ensure you are mocking Axios/Orval hooks correctly using tools like MSW (Mock Service Worker) or `vi.mock()`.*

## 🏗️ Architecture & Directory Structure

- `src/api/`: API integration layer.
  - `endpoints/` and `model/`: **DO NOT EDIT MANUALLY**. These are auto-generated by Orval.
  - `custom-instance.ts`: The Axios custom instance with auth interceptors. (Safe to edit).
- `src/layouts/`: Global wrapper components (e.g., `AuthLayout`, `MainLayout`).
- `src/pages/`: Route-specific page components (grouped by feature, e.g., `auth/`, `wardrobe/`).
- `src/components/`: Reusable, generic UI components (buttons, modals, inputs).
- `src/store/`: Zustand state management stores (e.g., `authStore.ts`).
- `src-tauri/`: Rust backend specifically for Tauri desktop/mobile system bindings.
- `api/`: Git submodule containing the single-source-of-truth OpenAPI spec.

## 📝 Code Style & Guidelines

### 1. React & TypeScript Standards
- **Functional Components**: Use functional components with standard `export default function ComponentName() {}` syntax instead of arrow functions for top-level exports.
- **Strict Typing**: Avoid using `any` or `ts-ignore`. Utilize the auto-generated types from `src/api/model/` whenever interacting with API data. If a generated type lacks a field, investigate the OpenAPI spec in the `api` submodule first.
- **Hooks**: Use generated TanStack Query hooks (e.g., `useGetWardrobe()`) from `src/api/endpoints/` for all network requests. Do not use raw `fetch` or `axios` directly in components unless for specialized tasks like binary S3 uploads.

### 2. State Management
- **Server State**: Always rely on TanStack Query (`useQuery`, `useMutation`) for remote data fetching, caching, loading states, and synchronization. Do not duplicate server state in Zustand.
- **Client/Global State**: Use Zustand (`src/store/`) for cross-component global state (like user authentication status or UI theme).
- **Authentication State (Event-Driven)**: AWS Amplify is the single source of truth for authentication. Zustand acts as a synchronous UI mirror. The `AuthListener` in `App.tsx` listens to Amplify Hub events (`signedOut`, `tokenRefresh_failure`) and automatically clears the local UI auth state. Always use `logout()` in `useAuthStore` to explicitly trigger `signOut()` from Amplify.
- **Local State**: Use `useState` or `useReducer` for simple, isolated UI state (e.g., modal visibility, form inputs).

### 3. Styling (Tailwind CSS v4)
- **Design Reference**: Read [DESIGN.md](DESIGN.md) for implemented colors, typography, components/states, and explicit gaps. Update affected sections with UI changes; keep future targets distinct from current behavior. Meta owns the reusable template and cross-project principles linked there.
- **Utility-First**: Strictly adhere to Tailwind utility classes.
- **Tailwind v4 Setup**: Note that v4 uses `@import "tailwindcss";` in the CSS file rather than the older `@tailwind` directives.
- **No Custom CSS**: Avoid adding styles to `index.css` or creating `.css` modules unless absolutely necessary. Rely entirely on Tailwind v4's arbitrary values (e.g., `w-[150px]`) if standard utilities fall short.
- **Class Merging**: When passing `className` props conditionally, prioritize clean template literals or utility libraries like `clsx` and `tailwind-merge`.

### 4. Naming Conventions
- **Components/Pages**: PascalCase (e.g., `WardrobePage.tsx`, `AddItemModal.tsx`). Keep names descriptive.
- **Files/Utilities**: camelCase (e.g., `authStore.ts`, `custom-instance.ts`).
- **Types/Interfaces**: PascalCase, typically matching the domain entity (e.g., `ClothingItem`).
- **Constants**: UPPER_SNAKE_CASE (e.g., `AXIOS_INSTANCE`, `MAX_FILE_SIZE`).
- **Hooks**: Prefix with `use` (e.g., `useAuthStore`, `usePostAuthLogin`).

### 5. Error Handling
- **API Errors**: Utilize the `error` object and `isError` boolean returned by TanStack Query's `useMutation` and `useQuery`. Do not rely solely on `try/catch` around the mutate functions unless using `mutateAsync`.
- **User Feedback**: Always provide visual feedback for errors (e.g., inline red text for form validation, toast notifications for global errors) rather than silent failures or raw `console.log`.
- **Global Interception**: Handle generic network errors (like 401 Unauthorized) within `src/api/custom-instance.ts` by intercepting the Axios response, clearing the Zustand auth store, and forcing a redirect to `/login`.

### 6. Imports
- Use a logical ordering to keep files clean and readable:
  1. Built-in React/Hooks (`import { useState } from 'react';`)
  2. Third-party libraries (`import { useNavigate } from 'react-router-dom';`)
  3. API Hooks and Models (`import { useGetWardrobe } from '../../api/endpoints/...';`)
  4. Local Components, Stores, and utilities (`import { useAuthStore } from '../../store/authStore';`)

## 🤖 Agent Operating Rules & Workflows

1. **API Synchronization Workflow**:
   If a frontend feature requires a backend change:
   - Make the route/schema change in `AnyWear-Service`, which is the API producer.
   - Generate and commit `api/anywear_openapi.yaml` from `AnyWear-Service`.
   - Update the Client's read-only `api` submodule pointer to that committed API revision.
   - Run `pnpm orval` in the `AnyWear-Client` root.
   - Inspect the newly generated interfaces in `src/api/model/` before utilizing the newly generated hook in your components.

2. **Never Assume Type Structures**:
   When fixing TypeScript errors involving API data (e.g., `Property 'imageUrl' does not exist on type 'GetWardrobe200Item'`), always use the `cat` or `read` tools to inspect the generated models in `src/api/model/` to understand the exact shape of the payload before guessing.

3. **Verify Everything**:
   After writing or refactoring code, run `pnpm tsc --noEmit` to ensure you haven't introduced type errors. Do not declare a task "complete" without verifying the types align.

4. **Preserve Submodule Integrity**:
   Treat the `api` submodule as a critical architectural boundary. Follow its `AGENTS.md` if present; Service producer instructions govern cross-repository API changes when it has no instruction file. Client only consumes a published exact API revision and must not edit or generate the shared specification.

5. **CI/CD Pipeline Monitoring**:
   Agents can use the `gh` CLI to check the status of GitHub Actions workflows. This is useful for verifying whether builds, tests, or deployments have succeeded or failed after pushing changes.
   - `gh workflow list` — list all workflows in the repository
   - `gh run list` — list recent workflow runs
   - `gh run view <run-id>` — view details of a specific run
   - `gh run watch <run-id>` — live-stream a run's progress
   - `gh run view <run-id> --log-failed` — view logs for failed steps only

## 🧪 Optional Local Browser Exploration (Playwright CLI)

Agents may drive the running application through `@playwright/cli` to inspect UI behavior, layout, loading states, and console errors. This exploratory smoke is optional and non-gating; it supplements applicable automated checks and does not replace regression tests or produce system release evidence. Record whether boundaries were mocked and any limitations. The real system E2E suite remains owned by `AnyWear-E2E` for Beta and later stages.

### Prerequisites

The Vite dev server must be running (serves the React frontend at `http://localhost:1420`):
```bash
pnpm dev
```

For Client-only validation, mock Service and cloud boundaries using the existing browser fixtures or network interception; no real Service or database is required. If the assigned scope includes exploratory interaction with an already available Service, verify its environment and resource ownership, point `VITE_API_BASE_URL` to it, and record that the observations are exploratory rather than release qualification.

Use pnpm for the CLI and browser installation:
```bash
pnpm exec playwright install chromium
pnpm dlx @playwright/cli --help
```

### Launching Playwright CLI

The agent drives the browser through `@playwright/cli` shell commands. Use `--headed` for this interactive local exploration, and inspect screenshots for visual regressions, layout bugs, z-index issues, and loading states. Automated browser checks may run headless.

```bash
pnpm dlx @playwright/cli open http://localhost:1420/login --headed
```

For persistent browser state across commands (cookies, localStorage, session), use the `--session` flag:

```bash
pnpm dlx @playwright/cli open http://localhost:1420/login --session anywear-test --headed
```

The following CLI subcommands are available for interacting with the app:

| Command | Usage |
|---------|-------|
| `open <url>` | Navigate to a route: `pnpm dlx @playwright/cli open http://localhost:1420/login --headed` |
| `snapshot` | Capture a structured ARIA tree of the current page |
| `click <selector>` | Click an element: `pnpm dlx @playwright/cli click "text=Dashboard" --headed` |
| `type <selector> <text>` | Type into an input: `pnpm dlx @playwright/cli type "input[type='email']" "test@anywear.local" --headed` |
| `fill` | Fill multiple form fields: `pnpm dlx @playwright/cli fill --field "email=..." --field "password=..." --headed` |
| `wait-for <selector>` | Wait for text/element to appear: `pnpm dlx @playwright/cli wait-for "text=Dashboard" --headed` |
| `eval <js>` | Execute arbitrary JS in page context (for mocking, state injection) |
| `console` | Read all browser console output |
| `screenshot` | Capture a screenshot: `pnpm dlx @playwright/cli screenshot --output evidence.png --headed` |

> For interactive local exploration, include `--headed` on `open`, `click`, `type`, and `fill`. This guidance does not change automated test or CI browser settings.

### Authentication for Testing

The app uses AWS Amplify SDK for authentication and obtains access tokens through `fetchAuthSession()`. Real identity flows use the app's `/register` and `/login` pages and belong in `AnyWear-E2E` for Beta and later stages.

**For scripted Playwright tests** (CI/regression): Client-owned tests mock Service and cloud boundaries and live in `browser/`. Real register-to-login and other Client + Service flows live in `AnyWear-E2E`.

**For mocked authenticated UI**: Reuse `authenticatedPage` from `browser/fixtures.ts` and `mockAmplifySession` from `browser/auth-session.ts`. They seed unsigned synthetic tokens into Amplify's SDK storage for a fixed fictitious pool/client and mock common Service endpoints. AuthGate still resolves the session through the real installed SDK; the Zustand mirror starts `false` and never reads a persisted UI flag. These tokens create no real Cognito identity and must only be used with mocked Service/cloud boundaries. The fixture and outfit/auto-tagging scenarios use `browser/mock-boundaries.ts` to intercept fixture images and reject unexpected external calls. Playwright's test server fixes the mocked API origin to `http://localhost:3000` and never inherits real Cognito settings.

### Mocking APIs

Use Playwright's `page.route()` before navigation, following `browser/fixtures.ts` and the existing `browser/*.spec.ts` examples. For example, a Client browser test can override the fixture's weather response:

```ts
await page.route('**/weather/current', (route) => route.fulfill({
  status: 200,
  contentType: 'application/json',
  body: 'null',
}));
await page.goto('/dashboard');
```

Orval requests use Axios in `src/api/custom-instance.ts`; patching `window.fetch` does not reliably intercept them. Use network interception for browser scenarios and MSW or `vi.mock()` for applicable unit/component tests. The unconnected legacy MCP harness, injected-string helpers and dated screenshot were retired; optional exploration uses the Playwright CLI instructions above and is not release evidence.

### Exploration Workflow

When local exploration is useful for the assigned change, follow this loop:

1. **Open** — `pnpm dlx @playwright/cli open <route> --session <name> --headed`
2. **Snapshot** — capture the ARIA tree to understand UI state
3. **Interact** — `click`, `type`, `fill` to drive the UI
4. **Observe** — `snapshot` again, verify expected elements appeared
5. **Check console** — `console` for errors and warnings
6. **Screenshot** — capture evidence with `screenshot --output ...`
7. **Report** — log any anomalies found

### Smoke Test

To inspect the dev server and login rendering before exploring a specific feature:

```bash
# 1. Start the dev server
pnpm dev

# 2. Open the app and verify it loads
pnpm dlx @playwright/cli open http://localhost:1420/login --session smoke --headed
pnpm dlx @playwright/cli wait-for "text=Sign in" --session smoke --headed
pnpm dlx @playwright/cli snapshot --session smoke --headed
pnpm dlx @playwright/cli console --session smoke

# 3. Capture a screenshot for evidence
pnpm dlx @playwright/cli screenshot --output browser/screenshots/smoke.png --session smoke --headed
```

This checks only that the dev server responds and the login page renders. It is optional local UI feedback and cannot satisfy a Beta or Production system release gate.
